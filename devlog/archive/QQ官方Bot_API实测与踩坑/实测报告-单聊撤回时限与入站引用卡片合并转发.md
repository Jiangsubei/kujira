# 实测报告：单聊消息撤回时限、入站引用、卡片与合并转发载荷

> **证据等级**：本文所有结论均来自 QQ 开放平台官方 Bot API v2 真实环境探针实测（对应探针：[`scripts/probe-c2c-gaps.ts`](../../../scripts/probe-c2c-gaps.ts) 与 [`scripts/lib/qq-probe-client.ts`](../../../scripts/lib/qq-probe-client.ts)）。所有用户标识、消息 ID 与下载凭证均已脱敏处理。
> **核心原则**：腾讯官方文档中的交互细节与真实线上下发结构（如引用、合并转发、`ark_data` 与撤回错误码）存在显著差异，工程实现必须以实测真实载荷与状态码为准。

---

## 1. 单聊消息撤回接口（`DELETE /v2/users/{openid}/messages/{message_id}`）实测

接口：`DELETE /v2/users/{openid}/messages/{message_id}`（鉴权头 `Authorization: QQBot <access_token>`）

| 用例编号 | 操作场景 | HTTP 状态 / 业务码 | 服务端响应 | 客户端表现 / 结论 |
| --- | --- | --- | --- | --- |
| **R1** | 发出纯文本（`msg_type=0`）1.5s 后撤回 | ✅ HTTP 200 | `{}` | 手机端机器人消息被成功撤回 |
| **R1_DUP** | 对同一已撤回出站 `id` 再次调用 `DELETE` | ✅ HTTP 200 | `{}` | 服务端撤回接口具备**幂等性** |
| **R2** | 发出 Markdown（`msg_type=2`）1.5s 后撤回 | ✅ HTTP 200 | `{}` | 支持撤回 Markdown 出站消息 |
| **R3** | 发出富媒体图片（`msg_type=7`）1.5s 后撤回 | ✅ HTTP 200 | `{}` | 支持撤回富媒体出站消息 |
| **R6** | 发出纯文本 1.5s 后调用 `DELETE ...?hidetip=true` | ✅ HTTP 200 | `{}` | 服务端正常受理返回 200（客户端是否差异隐藏灰字提示未单独对比区分） |
| **R5** | **发出纯文本 135 秒（2 分 15 秒）后调用 `DELETE`** | ❌ HTTP 400 / **`40064004`** | `{"message":"已经超出消息撤回时限","code":40064004}` | **严格强制 2 分钟（120 秒）撤回时限**，超时必拒 |
| **R7-入站ID** | 尝试用 `DELETE` 撤回用户发来的入站 `d.id` | ❌ HTTP 400 / **`40061002`** | `{"message":"请求参数msgid无效","code":40061002}` | 仅可撤回机器人自身出站 `body.id`，不可撤回用户消息 |
| **R7-伪造ID** | 尝试 `DELETE` 不存在的 `ROBOT1.0_nonexistent_...` | ❌ HTTP 400 / **`40061001`** | `{"message":"请求参数无效","code":40061001}` | 非法 `message_id` 返回 `40061001` |

**工程结论**：
1. 与被动回复不同，**单聊撤回确实严格执行 2 分钟（120s）硬时限**（超时报错 `40064004`），工具层与描述文档需如实保留 2 分钟撤回说明，且超限报错应透传给模型。
2. 出站接口返回的 `body.id` 是撤回唯一合法参数（被动消息响应 `body.id` 实测约 97 字符；主动消息响应 `body.id` 与入站 `d.id` 同为约 117 字符）；试图撤回入站 `d.id` 返回 `40061002`。

## 2. Gateway 事件基础字段与 `user_openid` 形态实测

通过真实 `READY` 与 6 条 `C2C_MESSAGE_CREATE` 事件观测：

1. **`READY` 事件结构**：`op=0, t="READY"`，携带 `d.session_id`、`d.user.id`（数字串）、`d.user.username`、`d.user.bot: true`。可用于插件运行态自识别机器人名称与在线状态，无需用户手填 `bot_qq`。
2. **`author` 对象字段**：包含 `["bot", "id", "union_openid", "user_openid", "username"]`（2026-11-18 补充探针新增观测到 `avatar` 字段）。
   - `user_openid`：实测为 **32 位纯大写十六进制字符串**（`^[0-9A-F]{32}$`），无连字符/下划线；
   - **`username` / `avatar` 变化记录**：2026-11-11 初次实测中 `username` 为空串 `""`、`union_openid` 为空串 `""`；但 **2026-11-18 补充实测（6 条事件全量）中，`author.username` 已下发真实非空昵称，且新增 `author.avatar` 头像 URL（`https://thirdqq.qlogo.cn/bqqthird?...`）**，`union_openid` 仍为空串 `""`。工程上应按「`username` 可能为空、也可能有值」兼容处理（有值时优先复用，缺失时回退）。
3. **`timestamp` 字段**：ISO-8601 带时区字符串（例：`2026-11-11T18:28:47+08:00`），并非 OneBot 秒级时间戳。
4. **主动消息（无 `msg_id`）复核**：`POST /v2/users/{openid}/messages` 不传 `msg_id`/`msg_seq` 在本测试 Bot 上同样 HTTP 200 成功。

## 3. 手机端用户「引用回复」入站载荷实测（`message_type: 103`）

用户长按消息点「引用」并发送文本回复时，Bot 收到 `C2C_MESSAGE_CREATE` 的真实特征如下：

### 场景 A：用户引用机器人此前发出的消息
- `d.message_type`: **`103`**
- `d.content`: 用户本次输入的回复文本（如 `"1"`）
- `d.message_scene.ext`: 同时包含两个键：
  - **`ref_msg_idx=REFIDX_...`** —— 与机器人当时出站响应 `body.ext_info.ref_idx` **完全一致**（135 字符）！
  - **`msg_idx=REFIDX_...`** —— 本条新入站消息自身的引用索引。
- 新增扩展字段：
  - `d.msg_elements`: 数组，项内直接携带被引用原消息的正文内容、类型与 `msg_idx`：
    ```json
    [
      {
        "content": "<被引用原消息内容>",
        "message_type": 103,
        "msg_idx": "REFIDX_..."
      }
    ]
    ```
  - `d.parallel_message`: `{ "msg_nodes": [{ "content": "[Markdown]", "message_type": 2 }] }`（标明原被引用节点的底层形态摘要）。

### 场景 B：用户引用一条自身已含引用的复合消息
- `d.message_type`: **`103`**
- `d.message_scene.ext` 中 `ref_msg_idx` 为 **`TMP_<uuid>`** 临时索引（而非永久 `REFIDX_...`）；
- 但 `d.msg_elements[0].content` **依然完整携带服务端展开的被引用上下文结构**：
  ```text
  === 消息 1 ===
  [消息内容] ...
  [消息类型] 引用消息
  [关联消息]
  --- 第1条 ---
      [消息内容] ...
  ```

**工程结论**：
- 入站解析引用关系时，优先提取 `message_scene.ext` 中的 `ref_msg_idx=`（当为 `REFIDX_...` 时可精确反查本地 SQLite `ref_idx` 列）；当 `ref_msg_idx` 为 `TMP_...` 或本地库未命中时，直接解析 `d.msg_elements[].content` 即可还原完整引用原文。

## 4. 入站「合并转发」（`message_type: 102`）实测

用户向单聊 Bot 转发一段包含文本、表情与多张图片的「合并转发聊天记录」时：

- `d.message_type`: **`102`**
- **关键真相**：QQ 官方平台**不会下发需要调接口展开的 `forwardId`**，而是由服务端**直接把合并转发展开成结构化纯文本放入 `d.content`**！格式示例（已脱敏）：
  ```text
  [群聊的聊天记录]
  === 消息 1 ===
  [消息内容] <正文文本>
  [发送者] <发送者昵称>

  === 消息 2 ===
  [发送者] <发送者昵称>
  [附件1] 类型:图片 文件名:<hash>.jpg 尺寸:1440x1920 大小:360.8KB URL:https://multimedia.nt.qq.com.cn/download?...&rkey=<已脱敏>&spec=0

  === 消息 3 ===
  [消息内容] <faceType=6,faceId="0",ext="<base64>">
  [发送者] <发送者昵称>
  [附件1] 类型:动图 文件名:<hash>.png 尺寸:240x240 大小:1.3MB URL:https://multimedia.nt.qq.com.cn/download?...&rkey=<已脱敏>&spec=0
  ```
- **内嵌图片 URL 裸 GET 实测**：从上述 `[附件1] ... URL:https://multimedia.nt.qq.com.cn/...` 提取首张图片 URL 发起**不带任何鉴权头的裸 `GET`**，实测返回 **`HTTP 200` / `Content-Type: image/jpeg` / 369,473 字节**。

**工程与安全警示**：
1. 嵌套图片 URL 以纯文本形式直接落在 `d.content` 且包含 `rkey` 访问凭证——入站归一化或按需拉取时**必须把 `URL:...` 从展示正文中剥离/脱敏**，避免将敏感凭证 URL 直接注入模型上下文或日志。
2. 如保留合并转发/资源拉取能力，可从 `message_type: 102` 的文本中提取内嵌下载链接直接裸 GET 落盘，无需 OneBot `get_forward_msg` 接口。

### 4.2 补充实测（2026-11-18）：群聊 vs 私聊来源、嵌套合并转发、内嵌引用与 `<attachmentType>` 壳

通过 `pnpm probe:quote` 被动采集 5 条不同类型的 `message_type: 102` 合并转发载荷（含 1 条普通文本对照组），确认以下线上真实行为：

#### 1. 群聊来源 vs 私聊来源合并转发对比
| 维度 | 群聊来源合并转发 | 私聊来源合并转发 |
| --- | --- | --- |
| `d.message_type` | `102` | `102`（完全相同） |
| 独立来源结构化字段 | **无**（`message_scene.source` 同为 `"default"`，`attachments` / `msg_elements` 均为空） | **无** |
| `d.content` 首行标题 | `[群聊的聊天记录]` | `[<用户A昵称>和<用户B昵称>的聊天记录]` |

**结论**：协议层**不提供**独立字段区分群聊/私聊合并转发，**唯一可区分的信号是 `d.content` 首行标题**（`[群聊的聊天记录]` vs `[<A>和<B>的聊天记录]`）。

#### 2. 嵌套合并转发（合并转发内包含子合并转发：2 层与 3 层实测）
实测确认：**QQ 官方平台对合并转发最多只展开最外层 1 层**，且**群聊来源与私聊来源对内层嵌套合并转发的折叠形态不同**，两种形态下内层正文、发送者、媒体全部丢失，无子 `forwardId`、无 `attachments`、无 `msg_elements`、无 URL、无 `msg_idx`，协议层面彻底无法二次展开或拉取：

1. **私聊合并转发内的嵌套合并转发（2 层）**：服务端将每条内层子合并转发折叠为一段重复的纯文本卡片占位：
   ```text
   [<用户A>和<用户B>的聊天记录]
   === 消息 1 ===
   [消息内容] <普通正文文本>
   [发送者] <用户A>

   === 消息 2 ===
   [消息内容] [卡片消息] 合并转发消息
   摘要: [聊天记录]
   [发送者] <用户B>
   [消息类型] 卡片消息
   [卡片消息] 合并转发消息 摘要:[聊天记录]
   ```
2. **群聊合并转发内的嵌套合并转发（2 层含图文混合 & 3 层嵌套）**：实测 2 层嵌套（第二层含图文混合）与 3 层嵌套（内层再套该 2 层记录）表现完全一致——服务端**连 `[卡片消息]` 摘要都不下发**，直接静默抽空，仅残留 `[发送者]` 行：
   ```text
   [群聊的聊天记录]
   === 消息 1 ===
   [发送者] <发送者A>

   === 消息 2 ===
   [消息内容] <正文文本>
   [发送者] <发送者B>
   ```

#### 3. 合并转发内嵌「引用消息」
合并转发内包含引用消息时，服务端会在对应节点下追加 `[关联消息]` 块，但被引用媒体仅给文本占位 `[图片]`，**不附带任何原图 URL 或附件行**：
```text
=== 消息 3 ===
[消息内容] <回复正文>
[发送者] <用户A>
[关联消息]
--- 第1条 ---
    [消息内容] [图片]
    [消息类型] 引用消息
```

#### 4. 合并转发图片节点出现 `<attachmentType=...>` 原始 XML 壳
在含多张图片（`.png` / `.webp`）的群聊合并转发中，图片节点不仅带 `[附件1]` 行，还可能在 `[消息内容]` 处附带原始 `<attachmentType=...>` 标签（其中 `description` 的 Base64 `eyJ0ZXh0IjoiW+WbvueJh10ifQ==` 解码为 `{"text":"[图片]"}`，且即便附件实际是 `.png`/`.webp`，`attachmentType` 字段仍固定写为 `"image/jpeg"`）：

```text
[群聊的聊天记录]
=== 消息 1 ===
[消息内容] <attachmentType="image/jpeg",attachmentIndex=0,description="eyJ0ZXh0IjoiW+WbvueJh10ifQ==">
[发送者] <发送者A>
[附件1] 类型:图片 文件名:<hash>.png 尺寸:800x612 大小:472.4KB URL:https://multimedia.nt.qq.com.cn/download?...&rkey=<已脱敏>&spec=0

=== 消息 2 ===
[消息内容] <attachmentType="image/jpeg",attachmentIndex=0,description="eyJ0ZXh0IjoiW+WbvueJh10ifQ==">
[发送者] <发送者A>
[附件1] 类型:图片 文件名:<hash>.webp 尺寸:1440x2560 大小:250.9KB URL:https://multimedia.nt.qq.com.cn/download?...&rkey=<已脱敏>&spec=0
```

**工程警示**：解析器不能只剥离 `<faceType=...>`，必须同步剥离 `<attachmentType=...>` 壳（尤其在同节点已存在 `[附件k]` 时），避免将原始标签与 Base64 字符串直接泄露进对话上下文。

## 5. 入站「卡片消息」（`message_type: 3` + `ark_data`）与 PNG 文件边界实测

1. **卡片 / 小程序分享（`message_type: 3`）**：
   - `d.content` 已由平台序列化为可读文本（`[卡片消息] <ark_name>\n摘要: ...\ntitle: ...\npreview: ...\nsource: ...`）；
   - 同时事件顶层直接附带结构化 **`d.ark_data`** 对象：
     ```json
     {
       "ark_name": "小程序",
       "ark_type": "miniapp",
       "fields": {
         "preview": "https://qq.ugcimg.cn/...",
         "source": "...",
         "source_logo": "https://...",
         "title": "..."
       },
       "prompt": "[QQ小程序]..."
     }
     ```
2. **`.png` 以 `content_type: "file"` 下发的情况**：
   - 实测一条入站附件 `attachments[0]` 为 `content_type: "file"`、`filename: "<HASH>.png"`、`size: 457027`，URL host 为 `grouptalk.c2c.qq.com`。说明即便后缀是 `.png`，只要经特定路径/文件形式发出，`content_type` 仍可能标为 `"file"`（落盘和识图路由应结合文件头魔数/扩展名综合判断）。

## 6. 诚实边界与仍未覆盖项

- **客户端撤回灰字差异**：`R6`（`?hidetip=true`）已确认服务端返回 HTTP 200 `{}`，但是否与 `R1` 在手机端存在“已撤回了一条消息”灰字差异未单独对比记录。
- **好友与拒收事件（`FRIEND_ADD` / `FRIEND_DEL` / `C2C_MSG_REJECT` / `C2C_MSG_RECEIVE`）**：本次测试未触发删加好友或拒收开关切换，其真实载荷与是否伴生入站欢迎消息仍属未实测项；工程上若收到非 `C2C_MESSAGE_CREATE` 事件应先安全记录脱敏事件名与关键标识，不盲猜私有字段语义。
