# 实测报告：单聊表情包渲染边界与非标准 `msg_type` 探测

> **证据等级**：本文结论均基于真实凭据与探针实测、以及桌面/手机端 QQ 客户端实际渲染截图核验得出（测试图片 `852×844` PNG `457,027 B`，对照缩放版 `160×158` PNG `27,902 B` 与 `96×95` GIF `4,277 B`）。
> **核心原则**：严禁将 QQ 客户端的「入站展示拆包」对称推测为「出站可逆协议」；目前实测确认 QQ 官方 Bot API v2 **不支持**下发「缩略小预览 + 原图高清查看」形态的自定义表情包消息。

---

## 1. 入站自定义表情包与出站渲染能力实测

### 1.1 入站事件真实载荷形态

用户从 QQ 客户端发送收藏/DIY 表情包给机器人时，Gateway `C2C_MESSAGE_CREATE` 下发的原始事件结构为：

- `message_type`: `0`
- `content`: `'<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">'`（其中 `ext` Base64 解码为 `{"text":""}`）
- `attachments[0]`: 标准 `image/*` 附件，**保留原图高分辨率尺寸**（实测见 `1254×1254` `image/jpeg`，`120,778 B`），且需按正常附件 URL 裸 `GET` 下载。

### 1.2 出站尝试复现“小预览大图”全量实验

针对 `file_type`、额外标识字段与 `msg_type=7` 组合发起以下实测：

| 实验组 | 请求载荷核心特征 | 服务端响应 | 客户端真实渲染效果 |
| --- | --- | --- | --- |
| **基线原图** (`T1`) | `upload_prepare(file_type=1)` + `msg_type=7` + `media.file_info`（`852×844` PNG） | ✅ HTTP 200 | 普通大图片（占满气泡常规图片宽度） |
| **携带入站标签** (`T2`) | `msg_type=7` + `media` + `content='<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">'` | ✅ HTTP 200 | 仍渲染为**普通大图**（未变表情包小图） |
| **附加扩展字段** (`T3` / `T4` / `T5a` / `T5b`) | 分别尝试顶层 `sub_type: 1`、`media.sub_type: 1`、顶层 `face_type: 6`、顶层 `type: 6` | ✅ HTTP 200 | 服务端均静默忽略扩展字段，**全部渲染为普通大图** |
| **缩图 PNG** (`T6`) | 先把原图物理缩放到 `160×158`（`27,902 B`）再走 `file_type=1` + `msg_type=7` | ✅ HTTP 200 | **气泡展示大小接近表情包，但图片本身真实降采样变糊**（点开亦为低清小图） |
| **极小 GIF** (`T6b`) | 缩放到 `96×95` GIF（`4,277 B`）再走 `file_type=1` + `msg_type=7` | ✅ HTTP 200 | 同为低分辨率小图（未呈现高清表情包特性） |
| **非常规 `file_type` 分片** | `upload_prepare` 传 `file_type = 0, 5, 6, 7, 8` | ⚠️ prepare 200，但四步流程**未获得 `file_info`** | 无法进入下发阶段 |
| **传统 `/files` 直传** | `POST /v2/users/{openid}/files`（`srv_send_msg=false` + `file_data` base64） | `file_type=1` ✅ 200；`file_type=5, 6` ❌ **HTTP 400 (`40093006 请求参数错误`)** | 服务端明确拒收 `file_type=5/6` |

### 1.3 结论与工程取舍

1. **协议能力边界确认**：QQ 官方 Bot API v2 **不支持**发出一张高分辨率图片并标记为「表情包形态（预览小图、点开高清原图）」。机器人在单聊中发出的本地图片均按普通图片消息渲染。
2. **展示大小与清晰度的工程权衡**：
   - 若直接发送库内原图（现行 `send_face` 行为），清晰度完整保留，但大尺寸图片在聊天窗中会显得偏大；
   - 若仅靠发送前物理降采样缩放（约 `160~168 px` 量级）缩小气泡显示面积，则会牺牲实际像素清晰度、放大查看变糊。后续需结合用户体验偏好决定保留原图还是提供可选发送缩放阈值。

## 2. 纯文本表情标签与非标准 `msg_type` 实测副作用

顺带验证了文档/社区常见文本内联表情语法以及非 `0/2/6/7` 的 `msg_type` 传参行为：

| 测试项 | 请求载荷核心特征 | 服务端响应 | 客户端真实表现（已截图确认） |
| --- | --- | --- | --- |
| **纯文本 `<faceType=6>`** (`T7`) | `msg_type=0, content='<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">'` | ✅ HTTP 200 | 未解析，直接按字面字符展示 |
| **文档 `<emoji:id>` 语法** (`T8`) | `msg_type=0, content='[T8] 系统小黄脸对照：<emoji:4> <emoji:14>'` | ✅ HTTP 200 | ❌ **单聊未生效**，客户端原样显示字面串 `<emoji:4> <emoji:14>` |
| **`msg_type=1`** (`MT-1`) | `{ msg_type: 1, media: { file_info } }` | ❌ HTTP 400 (`40034030 消息content字段不能为空`) | 发送失败 |
| **`msg_type=3`** (`MT-3`) | `{ msg_type: 3, media: { file_info } }` | ✅ HTTP 200 | ⚠️ **客户端隐形丢弃（未渲染出可见消息气泡）** |
| **`msg_type=4`** (`MT-4`) | `{ msg_type: 4, media: { file_info } }` | ✅ HTTP 200 | ⚠️ **图片未发出去，客户端渲染出一枚独立 QQ 小黄脸 `😲`（推断对应默认系统表情 0 号「惊讶」）** |
| **`msg_type=5`** (`MT-5`) | `{ msg_type: 5, media: { file_info } }` | ❌ HTTP 500 (`50015001 系统繁忙，请稍后重试`) | 发送失败 |
| **`msg_type=8`** (`MT-8`) | `{ msg_type: 8, media: { file_info } }` | ❌ HTTP 500 (`305011 card msg is nil`) | 缺少卡片字段失败 |

**附记**：
1. 腾讯官方文档提及的 `<emoji:id>` 在单聊 `msg_type=0` 文本中**并未按表情渲染**，不可依赖该写法在单聊发系统小黄脸；
2. 若后续需要支持发送 QQ 系统小黄脸表情，`msg_type=4` 触发默认 `😲` 的现象可作为另行设计探针的线索，但在完成专项字段验证前严禁臆测其载荷协议。
