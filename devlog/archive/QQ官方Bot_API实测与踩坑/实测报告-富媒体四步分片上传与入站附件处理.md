# 实测报告：富媒体四步分片上传与入站附件处理

> **证据等级**：本文结论均基于真实凭据与探针脚本（`scripts/probe-qq.ts`）实测得出。
> **核心原则**：腾讯富媒体上传文档在分片下标与分片大小描述上**存在直接会导致静默上传 0 字节的错误表述**，编码必须严格以以下实测语义为准。

---

## 1. 出站富媒体四步分片上传全链路实测

发本地图片、文件、语音、视频到 QQ 单聊（无公网 URL 时）必须走官方四步上传链路，再以 `msg_type=7` 下发：

1. **准备阶段**：`POST /v2/users/{openid}/upload_prepare`
   - 参数：`file_type`（`1` 图片 / `2` 视频 / `3` 语音 / `4` 文件）、`file_size`（字符串）、`file_name`、`md5`、`sha1`、`md5_10m`（文件前 `10002432` 字节的 MD5）。
   - 返回：`upload_id`、全局 `block_size`、`parts[]`（每项含 `index`、`presigned_url`、`block_size`）。
2. **分片上传**：向每个分片的 `presigned_url` 发起 **HTTP `PUT`**
   - 预签名 URL 域名实测落在 `qqbot-file-upload-1251316161.cos.accelerate.myqcloud.com`；
   - **裸 `PUT` + 二进制 body 即可返回 200**，无需附加任何鉴权或自定义 Header。
3. **分片确认**：`POST /v2/users/{openid}/upload_part_finish`
   - 参数：`upload_id`、`part_index`、`block_size`（字符串）、`md5`。
4. **合并获取 `file_info`**：`POST /v2/users/{openid}/files`
   - 参数：`{ upload_id }`。
   - 返回：`file_uuid`、`file_info`、`ttl`。
5. **消息下发**：`POST /v2/users/{openid}/messages`
   - 参数：`{ msg_type: 7, media: { file_info }, msg_id?, msg_seq? }`。

### 实测踩坑与必须遵守的 3 条硬规则

| 序号 | 官方文档错误表述 | 线上实测真相 | 按文档写的致命后果 |
| --- | --- | --- | --- |
| 1 | `parts[].index`「从 0 开始」 | **实测为 1-based（返回 `1`、`2`…）** | 若按 `index * blockSize` 算偏移，第 1 片直接跳到文件末尾上传 **0 字节**，合并时报错 **`850019 富媒体文件格式不支持`** |
| 2 | 分片大小「默认 5MB」 | **实测默认 `block_size = 10485760`（10 MB）** | 切勿硬编码 5MB，必须动态读取响应中的 `block_size` |
| 3 | 未强调单片 `block_size` 差异 | **每个 part 自带独立 `block_size`**（末片为余数，如 `12MB` 文件为 `10485760` + `2097152`） | `upload_part_finish` 若误报全局 `block_size`，将触发 **`850012 call inner proxy error`**，合并报 **`40093006 请求参数错误`** |

**正确实现方式**：将 `parts` 按 `index` 升序排序后，使用**累积偏移 `offset`**，每片取 `Number(part.block_size ?? globalBlockSize)` 切片，并在 `upload_part_finish` 中上报**该片自身的 `block_size`**。

## 2. `file_info` 缓存复用与“秒传”实测

使用 148,009 B 图片与 12 MB（12,582,912 B）二进制文件实测结果：

1. **`file_info` 有效期与可复用性**：
   - 合并接口返回的 `ttl` 实测为 **`86400` 秒（24 小时）**；
   - 使用同一个 `file_info` 在同一条 `msg_id` 下连续发送两次 `msg_type=7` 消息（配合递增 `msg_seq`），**均 200 成功且用户两次都收到文件**。
2. **同文件重传不触发服务端秒传**：
   - 将完全相同内容的 148,009 B 图片（相同 `md5` / `sha1` / `md5_10m`）完整重传一次，合并返回的 **`file_uuid` 不同**；
   - **结论**：不能假设仅传校验和即可跳过分片 PUT 上传；仅可在本地对已上传文件按 `(本地文件身份)` 在 `ttl` 窗口内缓存复用 `file_info`。

## 3. 入站附件下载与语音字段实测

用户发送图片、文件、语音时，通过 `C2C_MESSAGE_CREATE` 事件 `attachments[]` 传入：

| 入站类型 | `content_type` | `filename` 特征 | 下载 URL Host | 裸 GET（无鉴权头） | 带 `QQBot` Token |
| --- | --- | --- | --- | --- | --- |
| 图片 | `image/png` 等 | 哈希文件名（如 `95C5…A03B7A.png`） | `multimedia.nt.qq.com.cn` | ✅ 200 | ✅ 200（同结果） |
| 文件 | `file` | **保留真实文件名** | `grouptalk.c2c.qq.com` | ✅ 200 | ✅ 200（同结果） |
| 语音 | `voice` | 哈希名 + `.amr` | `multimedia.nt.qq.com.cn` | ✅ 200 | ✅ 200（同结果） |
| 语音 WAV 转码地址（`voice_wav_url`） | — | — | `qqbot.ugcimg.cn` | ✅ 200（`audio/x-wav`） | — |

### 关键实测细节

1. **无需鉴权头即可下载**：入站附件 URL 自带访问凭证查询串，直接裸 `GET` 即可下载（`message_scene.ext` 中实测无 `auth_token`）。注意落盘日志中不要明文打印带 query 凭证的完整 URL。
2. **原始语音 HTTP 响应头不可信**：语音原始 `url` 落盘为 `.amr`（如 2,839 B），但下载响应头 `Content-Type` 错报为 `audio/mp3`。应**以事件里的 `content_type` 字段为准**，并优先直接下载 **`voice_wav_url`** 获取标准 `audio/x-wav`（如 68,238 B WAV），无需自行集成 SILK/AMR 解码器。
3. **官方自带语音转写文本**：语音附件实测携带 **`asr_refer_text`** 字段（直接包含语音转写文字），可直接随消息上下文注入模型。
4. **文件名安全处理**：`file` 类型的 `filename` 属于外部可控输入，落盘前必须执行 `path.basename` 与危险字符净化以防路径穿越。
