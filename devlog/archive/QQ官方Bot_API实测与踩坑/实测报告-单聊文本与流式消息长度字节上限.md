# 实测报告：单聊普通消息与流式消息长度及字节上限

> **证据等级**：本文结论均基于真实凭据与探针脚本（`scripts/probe-e3-length.ts`、`scripts/probe-qq.ts`）实测得出。
> **方法说明**：实验使用短消息对照（在长消息触发失败后立即补发一条短消息）以排除频控或额度耗尽导致的假阴性，并采用 CJK（1 字符 = 3 字节 UTF-8）与 ASCII（1 字符 = 1 字节 UTF-8）双填充曲线夹逼，区分“按字符计数”还是“按字节计数”。

---

## 1. 实测结论总表

| 通道 / 场景 | 实测阈值 / 行为 | 失败码 / 响应 | 结论说明 |
| --- | --- | --- | --- |
| **流式单次请求 `content_raw` 上限** | **`[20414, 20426)` UTF-8 字节（≈ 20 KiB）** | HTTP 400 / `code=40054018` (`消息发送失败，消息过长或异常`) | **严格按 UTF-8 字节数计数**，与字符/码点数无关 |
| **单条流式累积正文总量** | **≥ 20,000 CJK 字符（≈ 60,000 字节）未触限** | 全程 HTTP 200 | 单次请求上限不作用于整段流累积总量 |
| **流式 `remain_msg_len` 返回字段** | 696 字符及 20,000 字符流式中**全程恒为 `0`** | `remain_msg_len: 0` | **该字段不可作为长度预算依据** |
| **流式空 `content_raw` 片段** | 发送 `content_raw: ""` 片段 | HTTP 200 | 服务端接受空串片段（如结束帧） |
| **普通 Markdown（`msg_type=2`）单条上限** | **≥ 32,000 CJK 字符（= 96,000 字节）未触限** | HTTP 200 | 真实上限未探明，但远高于常规单条回复需求 |
| **普通纯文本（`msg_type=0`）单条上限** | **≥ 16,000 CJK 字符（= 48,000 字节）未触限** | HTTP 200 | 真实上限未探明 |

## 2. 流式单次请求字节上限夹逼原始数据

对同一流式端点发送首片大负载，用二分夹逼测得两种编码填充的临界点：

| 填充字符类型 | 最大成功长度 | 最小失败长度 | 折算 UTF-8 字节范围 |
| --- | --- | --- | --- |
| CJK 汉字（`填`，3 字节/字） | 6,781 字符（**20,333 B**） | 6,812 字符（**20,426 B**） | — |
| ASCII 字符（`a`，1 字节/字） | 20,406 字符（**20,414 B**） | 20,437 字符（**20,445 B**） | **交集 `[20414, 20426)` B** |

ASCII 最大成功字符数是 CJK 的约 3 倍，而两条曲线的字节临界点完全重合在 **≈ 20.4 KB（20 KiB 附近）**，确凿证明平台限制维度为 **UTF-8 字节数**而非字符数。

## 3. 流式 `append` 与 `replace` 模式实测特征

接口：`POST /v2/users/{openid}/stream_messages`

1. **`append` 与 `replace` 两种模式均可正常使用**：
   - 客户端表现均为“同一条消息气泡原地递增刷新”；
   - **首片即时可见**（`input_state=1` 发出后即在手机端展示，无需等到 `input_state=10`）。
2. **`replace` 模式前缀强约束**：
   - `replace` 每次需传递累积全文，且**必须以此前已下发成功的内容为严格前缀**；
   - 一旦改动前文任意字符（例如将「分片 1/20」改为「分片 2/20」），服务端立即拒收：**`40007 已经提交的消息内容不可修改`**。
3. **`append` 模式注意事项**：
   - 仅发送增量片段，天然规避 `40007`；
   - 分片序号 `index` 由调用方从 0 开始跨 step 单调递增维护，首片成功后将服务端返回的 `id` 作为后续分片的 `stream_msg_id` 传入。

## 4. 工程设计警示与诚实边界

1. **禁止按固定字符数做整段静默截断**：
   - 历史经验踩坑：曾以 `4000` 码点作为整段 Markdown 截断上限，导致长回复被静默丢弃后半段；
   - 正确做法：单次请求防护应以 **UTF-8 字节数**为基准（例如流式单次分片设防在 8 KiB、普通消息切条阈值设防在 16 KiB），**超限时按码点/换行边界切分为多片/多条发送，绝不丢字**。
2. **未定界边界**：
   - 普通消息（`msg_type=0`/`2`）在 96 KB 以内均未触限，最终硬上限常数未继续加压；
   - 流式单次上限精确字节常数（`[20414, 20426)` 区间内具体是 `20480` 扣除包裹开销还是固定值）未进一步细拆。
