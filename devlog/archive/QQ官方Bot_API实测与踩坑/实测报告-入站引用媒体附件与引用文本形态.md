# 实测报告：入站引用媒体附件与引用文本形态（`message_type=103`）

> 采集时间：2026-11-12
> 采集方式：`pnpm probe:quote`（被动抓取，不回复任何消息；产物写入 `logs/probe/`，该目录已在 `.gitignore` 内）
> 脱敏说明：本文所有真实 openid / msg_id / ref_idx / rkey / 昵称 / 文件名均已替换为占位符，不包含任何真实隐私信息。

---

## 1. 探针场景

对同一机器人依次执行以下真实操作，逐条抓取 `C2C_MESSAGE_CREATE` 原始载荷：

| # | 操作 | 入站 `message_type` |
|---|---|---|
| 1 | 直发一张图片 | `0` |
| 2 | 引用刚才那张图片 + 文字回复 | `103` |
| 3 | 直发一个短视频 | `0` |
| 4 | 引用该视频 + 文字回复 | `103` |
| 5 | 直发一个文件（`.md`） | `0` |
| 6 | 引用该文件 + 文字回复 | `103` |
| 7 | 发送一条含链接的纯文本 | `0` |
| 8 | 引用该链接文本 + 文字回复 | `103` |
| 9 | 合并转发一段聊天记录（仅文字与系统表情） | `102` |
| 10 | 引用该合并转发 + 文字回复 | `103` |
| 11 | 引用机器人此前发出的图片 | `103` |
| 12 | 发送一条纯文本消息 | `0` |
| 13 | 引用该纯文本 + 文字回复 | `103` |

补充采集（第二批，合并转发含媒体）：

| # | 操作 | 入站 `message_type` |
|---|---|---|
| A | 合并转发一段**含图片**的聊天记录 | `102` |
| B | 引用该含图片的合并转发 + 文字回复 | `103` |
| C | 直发一个 `.psd` 文件（对照文件分类） | `0` |

## 2. 关键结论（与既有文档认知的差异）

### 2.1 引用媒体消息时，官方直接下发**结构化附件**

引用图片（#2）的真实形态：

```json
{
  "msg_elements": [
    {
      "content": "",
      "message_type": 103,
      "msg_idx": "<REFIDX...>",
      "attachments": [
        {
          "content_type": "file",
          "filename": "<hash>.png",
          "size": 457027,
          "url": "https://grouptalk.c2c.qq.com/<已脱敏>"
        }
      ]
    }
  ],
  "parallel_message": { "msg_nodes": [{ "content": "[图片]", "message_type": 7 }] }
}
```

引用视频（#4）同构，`filename` 为 `<hash>.mp4`，`content_type` 仍为 `"file"`。

引用机器人发出的图片（#11）则为：

```json
{
  "attachments": [
    {
      "content_type": "image/jpeg",
      "filename": "<hash>.jpeg",
      "size": 97646,
      "width": 1254,
      "height": 1254,
      "url": "https://multimedia.nt.qq.com.cn/download?<已脱敏>"
    }
  ],
  "parallel_message": { "msg_nodes": [{ "content": "[图片]", "message_type": 7 }] }
}
```

**结论：引用媒体不需要「从引用正文文本里解析 URL」，可以直接复用与直发消息完全同构的
`QQAttachment` 落盘管线。**

### 2.2 引用媒体消息时 `content` 为空串

- 引用图片 / 视频 / 文件（#2 / #4 / #6）时，`msg_elements[0].content` 均为 `""`；
- 引用纯文本（#13）时，`content` 为原文；
- 引用合并转发（#10）时，`content` 为 `=== 消息 1 === ...` 的完整引用结构（本次样本无 `[附件k]` 行，因被转发的记录只有文字与系统表情）。

### 2.3 引用**文件**时 `attachments` 缺失（#6）

```json
{ "message_type": 103, "msg_idx": "<REFIDX...>" }
```

仅能从 `parallel_message.msg_nodes[0].content` 得到 `"[文件]"` 形态摘要，**没有任何下载地址**。
→ 引用文件在官方未下发附件时无法落盘，只能展示形态摘要，不得臆造下载或空直链。

### 2.4 引用**链接文本**时链接只出现在 `parallel_message`（#8）

```json
{
  "msg_elements": [{ "message_type": 103, "msg_idx": "<REFIDX...>" }],
  "parallel_message": { "msg_nodes": [{ "content": "https://example.com/repo", "message_type": 0 }] }
}
```

`msg_elements[0].content` 为空，链接仅在 `parallel_message.msg_nodes[0].content`。
→ 引用正文兜底顺序必须为：`msg_elements[].attachments`（本地化）→ `msg_elements[].content` →
`parallel_message.msg_nodes[].content`。

### 2.5 直发图片/视频/文件实测同样为 `content_type: "file"`

| 直发内容 | `content_type` | `filename` | `width/height` |
|---|---|---|---|
| 图片 | `file` | `<hash>.png` | 无 |
| 视频 | `file` | `<hash>.mp4` | 无 |
| 文件 | `file` | `<原文件名>.md` | 无 |

与既有归档「`.png` 以 `content_type: "file"` 下发」一致。**本次已按扩展名改判**：`content_type='file'`
的 `.png` / `.mp4` 分别回归 `image` / `video`（落盘 `image/`、`video/`，渲染 `[图片:...]`、`[视频:...]`）；
无法识别的扩展名仍保持 `file`。落盘后仍以字节魔数校正真实 `format` 字段。

### 2.6 合并转发无媒体时不会生成 `[附件k]` 行

#9 的 `content` 只有 `=== 消息 N ===` / `[消息内容]` / `[发送者]`，没有任何 `[附件k]` 行。
含媒体的合并转发形态见 2.7（第二批实测已补齐）。

### 2.7 合并转发含图片的真实形态（第二批 A）

```text
[群聊的聊天记录]
=== 消息 1 ===
[消息内容] <文字消息>
[发送者] <昵称A>

=== 消息 2 ===
[消息内容] <文字消息>
[发送者] <昵称B>

=== 消息 3 ===
[消息内容] <文字消息>
[发送者] <昵称C>

=== 消息 4 ===
[发送者] <昵称D>
[附件1] 类型:图片 文件名:<hash>.jpg 尺寸:1370x1920 大小:221.0KB URL:https://multimedia.nt.qq.com.cn/download?<已脱敏>
```

要点：
- 纯图片节点**没有 `[消息内容]` 行**，只有 `[发送者]` + `[附件k]`；
- 附件行携带 `类型` / `文件名` / `尺寸` / `大小` / `URL`，图片 URL 宿主为 `multimedia.nt.qq.com.cn`；
- 既有 `formatForwardMessageContent` 对这种「无正文节点」解析正确，输出 `N. <发送者>: [图片:<本地路径>]`（已用真实结构做本地验证）。

### 2.8 引用**含媒体**的合并转发时无法展开（第二批 B）

引用一条含图片的合并转发，官方载荷为：

```json
{
  "message_type": 103,
  "msg_elements": [{ "message_type": 103, "msg_idx": "<REFIDX...>" }],
  "parallel_message": { "msg_nodes": [{ "content": "[文件]", "message_type": 7 }] }
}
```

对比第一批 #10（引用**纯文字**合并转发）：

| 被引用的合并转发 | `msg_elements[0].content` | `attachments` | `parallel_message` |
|---|---|---|---|
| 纯文字 / 系统表情 | ✅ 完整 `=== 消息 N ===` 展开结构 | ❌ | 展开结构 |
| **含图片等媒体** | ❌ 空串 | ❌ | `[文件]`（`message_type: 7`） |

**结论：合并转发一旦包含媒体，引用时官方只给 `[文件]` 形态摘要，既没有正文结构也没有附件，
无法二次展开或落盘。** 只能按 `parallel_message` 展示 `[文件]`，不得臆造 `=== 消息` 结构或发起下载。

## 4. 遗留与边界

1. ✅ 「合并转发含图片」形态已由第二批实测补齐（见 2.7），无正文节点的解析已验证；
2. 引用文件缺失 `attachments` 属官方未下发，无法落盘，只能展示 `[文件]` 摘要；
3. 引用**含媒体**的合并转发时官方只下发 `[文件]` 摘要（见 2.8），无法二次展开或下载，属官方限制；
4. 文本中的裸链接（非 `URL:` 标记 / 非 QQ CDN 白名单）不做下载，原样保留在引用正文；
5. `content_type='file'` 的图片/视频已按扩展名改判为 `image` / `video`；无扩展名或无法识别的仍保持 `file`，
   真实格式最终以落盘后的字节魔数为准。
