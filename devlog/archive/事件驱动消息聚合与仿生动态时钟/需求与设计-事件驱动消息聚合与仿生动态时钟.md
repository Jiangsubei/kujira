# 需求与设计：事件驱动单聊消息聚合与仿生动态时钟

> **创建日期**：2026-11-14  
> **状态**：方案已定稿，进入分批开发阶段  
> **适用范围**：kujira QQ 官方 Bot C2C 单聊会话

---

## 1. 目标与背景

当前系统的消息聚合与冷场搭话依托于一个全局固定自由时钟（例如固定 60 秒轮询、固定 2 分钟检查周期）。这存在两个体验痛点：
1. **机械感强**：等待时长脱离真实聊天语境，用户发信时恰逢 tick 前或刚 tick 完，导致等待延迟方差极大且不可控；
2. **缺乏拟人节奏**：真人聊天具备热度惯性（连聊时秒回、连发时插话抢话、摸鱼时慢回、潜水搭话随机）。

本次重构将消息聚合与冷场主动搭话升级为：**基于 Peer 独立的事件驱动时序器 + 仿生随机区间 + 动态热度折减与下限锁定机制**。

## 2. 配置项定义与 UI 呈现规范

### 2.1 配置字段设计

放弃原先单一生硬的固定分钟数配置，改为两组明确区间 + 分段偏好 + 秒回开关：

| 字段名 | 类型 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `aggregation_enabled` | `boolean` | `false` | 连续消息聚合回复总开关 |
| `aggregation_min_seconds` | `number` | `10` | 聚合等待最小时长（秒，硬底线） |
| `aggregation_max_seconds` | `number` | `60` | 聚合等待最大时长（秒） |
| `idle_reply_enabled` | `boolean` | `false` | 冷场主动搭话总开关 |
| `idle_reply_min_mins` | `number` | `30` | 潜水主动搭话最小沉默时长（分钟） |
| `idle_reply_max_mins` | `number` | `120` | 潜水主动搭话最大沉默时长（分钟） |
| `proactive_attitude` | `'enthusiastic' \| 'balanced' \| 'aloof'` | `'balanced'` | 互动偏好分段（热情 / 均衡 / 冷淡） |
| `instant_reply_enabled` | `boolean` | `false` | 允许在连续热聊时概率秒回（突破聚合下限） |

> **向后兼容性**：旧配置项 `aggregation_interval_mins` 与 `idle_reply_timeout_mins` 在升级迁移或缺省时，映射为默认区间（例如 2 分钟映射为 `[10s, 60s]`，60 分钟映射为 `[30m, 120m]`）。

### 2.2 WebUI 组件规范
- **互动偏好（proactive_attitude）**：在 DSH 设置页中采用**分段单选按钮组（Segmented Control）**呈现，包含三个选项：`[ 热情 | 均衡 | 冷淡 ]`，选中的项带高亮边框和激活色块；
- **区间输入**：采用成对数值输入框；
- **秒回开关**：独立 Switch 字段，清晰标注文案：`允许在连续热聊时概率秒回 (instant_reply_enabled)`，提示文本注明“开启后在高活跃度下允许突破下限，在 0~2 秒内极速响应”。

## 3. 双层活跃度度量体系 (Activity & Momentum)

活跃度用于动态调制初始等待时长的采样分布、折减比例以及秒回判定。

### 3.1 微观响应时效 ($\Delta t_{turn}$)
- **定义**：当前入站消息到达时间戳 $t_{in}$ 与上一轮 Bot 出站消息时间戳 $t_{bot\_out}$ 的差值：
  $$\Delta t_{turn} = t_{in} - t_{bot\_out}$$
- **判定语义**：
  - $\Delta t_{turn} \le 15\text{s}$：极速接话，说明对方正在手机前注视聊天；
  - $15\text{s} < \Delta t_{turn} \le 120\text{s}$：正常连贯聊天；
  - $\Delta t_{turn} > 120\text{s}$：摸鱼/切屏/异步对话。

### 3.2 宏观历史动量 (Past $X$ Completed Turns)
- **拒绝死板时间窗口**：不看“过去 15 分钟内”，避免因刚冷场片刻而读出空白历史；
- **回溯最近已完成轮次**：从 DSH 会话事件或数据库中读取**最近 $X$ 轮（默认 3~5 轮）已完成的 Agent 交互**：
  - 提取每轮用户从 Bot 回复到再次发话的时延；
  - 提取每轮用户发信的消息密度（单轮多条还是单发）；
  - 计算平均交互节奏指数 $M_{macro} \in [0, 1]$。

### 3.3 综合活跃度评分
综合微观与宏观因子加权得出当前会话的综合活跃度 $\text{Score}_{act} \in [0, 1]$（0 代表极冷淡/异步，1 代表极热烈/在席）。

## 4. 核心时序引擎与状态机

### 4.1 偏好（Attitude）的数学映射
设当前区间为 $[min, max]$，随机数 $r \in [0, 1]$：
- **偏置系数 $p$**：
  - `enthusiastic`（热情）：$p = 2.0$（采样偏向 $min$，反应迅速、潜水间隔短）；
  - `balanced`（均衡）：$p = 1.0$（均匀随机）；
  - `aloof`（冷淡）：$p = 0.5$（采样偏向 $max$，节奏沉着、留白多）。
- 结合会话活跃度 $\text{Score}_{act}$ 进一步微调偏置系数 $p$。
- 随机采样公式：
  $$\text{Duration} = min + (max - min) \cdot r^p$$

### 4.2 聚合周期时序状态机

每个 Peer 维护独立的时钟与池状态：
```ts
interface PeerTimingState {
  pending: AggregatedMessage[];
  lastFromUser?: string;
  delivering: boolean;
  
  // 聚合倒计时控制
  cycleStartTime: number | null;    // 本轮周期启动时刻
  targetWakeupAt: number | null;    // 当前目标触发时刻
  floorWakeupAt: number | null;     // 绝对硬底线时刻 (cycleStartTime + T_min)
  isFloorLocked: boolean;           // 是否已触底下限锁定
  timer: NodeJS.Timeout | null;     // 独立定时器句柄
  
  // 潜水主动搭话控制
  idleTargetWakeupAt: number | null; // 目标冷场唤醒时刻
  idleTimer: NodeJS.Timeout | null;  // 潜水定时器句柄
}
```

#### 流程 1：空闲首次入站 (First Inbound)
1. 会话当前无活动定时器，首条消息在 $t_0$ 到达入池；
2. **秒回评估**：
   - 若 `instant_reply_enabled === true`，且当前处于高活跃度（$\text{Score}_{act} \ge 0.7$）：
   - 按概率判定为秒回（例如 $40\% \sim 70\%$ 概率），立即触发唤醒（或 $1\sim 2$ 秒微延时唤醒），跳过常规等待；
3. **常规聚合启动**：
   - 依据偏好与活跃度在 $[T_{agg\_min}, T_{agg\_max}]$ 采样得到初始等待时长 $D_0$；
   - 设定：
     $$\text{TargetTime} = t_0 + D_0$$
     $$\text{FloorTime} = t_0 + T_{agg\_min}$$
   - 启动定时器，等待 TargetTime。

#### 流程 2：周期内追加消息（温和折减 + 下限锁定）
1. 在倒计时未到期前，新消息到达并入池；
2. **若 `isFloorLocked === true`**：
   - **直接将消息推入 pending 队列，绝不修改当前定时器，直接返回**；
3. **若尚未锁定**：
   - 将当前距 TargetTime 的剩余时间温和折减 25%~30%：
     $$\text{Remaining} = \text{TargetTime} - now$$
     $$\text{NewRemaining} = \text{Remaining} \times 0.75$$
     $$\text{NewTargetTime} = now + \text{NewRemaining}$$
   - **触底判定**：
     - 若 $\text{NewTargetTime} \le \text{FloorTime}$：
       - 将目标时刻修正并锁定：$\text{TargetTime} = \text{FloorTime}$；
       - 标记 `isFloorLocked = true`；
       - 重设物理定时器至 $\text{FloorTime}$；
     - 否则：
       - 更新 $\text{TargetTime} = \text{NewTargetTime}$，重设定时器。

> **核心价值**：一旦被多条消息压缩到底限 $\text{FloorTime}$，之后用户连发再多消息也不会再把时间往后拖延，到点立刻打断投递，彻底解决饥饿延迟并自然形成拟人的半截插话。

#### 流程 3：一轮 Agent 运行完毕 (Turn End Flush & Reset)
1. Agent 触发 `session/event` 的 `turn/end` 事件；
2. 若池内有未处理的新消息（运行期间排队到来的）：
   - 立即执行轮次边界 flush（`reason = 'turn_end'`）；
3. 若池空：
   - 清除聚合周期状态；
   - **重置潜水闹钟**：依据偏好与历史动量在 $[T_{idle\_min}, T_{idle\_max}]$ 内投掷下一个冷场唤醒目标时刻，挂载潜水定时器。

#### 流程 4：潜水超时唤醒 (Lurk Wakeup)
1. 潜水定时器到点；
2. 校验门控：
   - 未在等待用户输入（提问/审批）；
   - 内存池中无新未发消息；
   - 存在有效入站被动回复锚点（严防纯主动消息 `50015001`）；
3. 分发 `idle_reply` 系统事件，唤醒模型；由模型自主研判是主动找话题还是输出 `[结束]`。
