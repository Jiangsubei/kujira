## 1. 最终架构（第四次修订：内存池 + 轮次边界注入）

### 1.1 纯内存消息池

聚合开启时，入站普通消息不再只置布尔标志，而是进入**纯内存池**：

```ts
interface PeerState {
  pending: AggregatedMessage[];    // 尚未投递的消息（按时间升序）
  lastFromUser?: string;           // 池内最后一位真实发送者（审批发起人）
  delivering: boolean;             // 投递单飞锁
  lastIdleWakeupAt: number | null; // 上次冷场唤醒时刻
}
```

池只装「尚未投递」的真实入站消息，每条包含短 ID、正文、时间、引用快照与附件占位符。
数据库仍是历史记录的**唯一可信源**，但聚合回复不再要求模型自己去查库。

### 1.2 逐条注入，而不是只喊「去看历史」

系统事件直接携带消息快照，提示词逐条列出（短 ID + 时间各占抬头，引用与附件各占一行）：

```text
系统事件：[消息聚合] [2026-11-13 15:45:22]

会话状态：自你上次回复以来，用户发来了 3 条新消息。

1. [msg_12] [2026-11-13 15:44:01] 在吗
2. [msg_14] [2026-11-13 15:44:18] 等会再去
3. [msg_13] [2026-11-13 15:44:30]
   [引用回复: "[msg_10] [2026-11-13 15:44:00] 那个视频"]
   [图片: /tmp/kujira/xxx.png]
   我刚看完那个视频

（说明：以上是本轮周期内聚合的用户消息，已按时间顺序逐条列出，可直接针对内容回复；
如需回顾更早的上下文，可调用 read_chat_history 查询。若此时回复会打扰用户，
或没有值得回应的内容，直接输出 [结束] 即可。……）
```

纯文本消息的正文与消息头**同一行**，与正常直接入站消息的格式完全一致；
只有带引用或附件的消息才把消息头单独起行，引用、附件、正文依次缩进排列。

`read_chat_history` 保留为**可选回溯**，不再是必经步骤。

### 1.3 只在轮次边界投递

| 时机 | 触发 | 事件 `reason` | 投递方式 |
| --- | --- | --- | --- |
| 会话空闲，自由周期到点 | `checkProactive` tick | `period` | `followup` 开新轮 |
| 一轮运行结束 | `session/event` → `turn/end` | `turn_end` | 强制 `followup` 排队下一轮 |

- **运行中的 tick 绝不打断**：`isAgentRunning(peer)` 为真时池保留，等 `turn/end`；
- **聚合批次永不 steer**：`agent-runner` 对 `trigger === 'aggregated'` 强制 `followup`；
- **turn/end flush 的提示词**换成「你上一轮处理期间又来了 N 条」，并明确引导：
  已被上一条回复覆盖、或只是补充/闲聊/情绪表达时，直接输出 `[结束]`，不要重复回复。

### 1.4 投递成功后才清空

- 投递前取**快照**，投递成功后只移除快照内的消息；
- 投递期间新到的消息留在池内，等待下一次投递；
- 投递抛错、`ensureSession` 失败 → 整批保留，下一次 tick / flush 重试；
- 同一 peer 用 `delivering` 单飞锁串行，tick 与 turn/end 并发不会重复投递。

### 1.5 入站分流矩阵

| 场景 | `steer` | `queue` |
| --- | --- | --- |
| 聚合关闭 | 即时 `dispatchWakeup`（原逻辑） | 即时 `dispatchWakeup`（原逻辑，逐条 followup） |
| 聚合开启 + 会话空闲 | 入池，等周期 tick | 入池，等周期 tick |
| 聚合开启 + 一轮运行中 | **不入池**，`dispatchWakeup` → `agent.steer` 即时插话 | 入池，等 `turn/end` flush |

分流判定收敛在纯函数 `shouldPoolInbound()`（`src/gateway/proactive.ts`），由 `index.ts` 调用。

### 1.6 为什么这样能解决提问 / 审批的问题

- 提问答案、审批 `y/n` 在拦截 3/4 被消费，**根本不入池**；
- `wait_for_user_messages` 收集的消息在拦截 2 被投递给 registry，**不入池、不 steer**；
- 因此注入给模型的历史里不会出现已经处理过的答案，模型不会对 `y`、选项序号再回复一遍；
- 提问/审批挂起期间 tick 与 flush 都跳过，池完整保留，恢复后由 `turn/end` 一并投递。

### 1.7 聚合关闭时清空池

聚合开关被关闭时，池失去投递通道，直接清空（消息仍在 DB，可用 `read_chat_history` 捡回），
避免下次开启聚合时一次性投递很久以前的消息。

## 3. 入站判定顺序

```
入站 C2C_MESSAGE_CREATE
 ├─ 斜杠命令                    → 立即执行并回执
 ├─ wait_for_user_messages 等待中 → 立即投递收集器（不入池）
 ├─ 提问回复                    → 立即消费（不入池）
 ├─ 审批回复 y/n                → 立即消费（不入池）
 ├─ 聚合开启？
 │   ├─ 一轮运行中 + steer      → 即时 dispatchWakeup（agent.steer）
 │   └─ 其他                   → 入池（落库 + trackInboundContext）
 └─ 其余（聚合关闭）            → 即时唤醒 Agent
```

## 4. 冷场主动搭话（不变）

### 4.1 会话口径

候选集 = `peer_openid_map` 中已登记的 peer。有记录但无活跃会话 → `ensureSession` 后唤醒；
无任何记录 → 绝不新建。

### 4.2 发信通道

取该 peer 最后一条入站 `msg_id` 做被动回复；内存锚点未命中则回落
`db.getLatestValidInboundSlot`；两者都拿不到就跳过本轮，绝不降级为纯主动消息。

### 4.3 沉默起点与重复唤醒

以库中最新入站消息时间为准。出站消息不写入该时间。两道闸门同时满足才再次唤醒：

- 距最近一次入站已满 `idle_reply_timeout_mins`；
- 距上次冷场唤醒也已满同一个周期（本进程内首次没有这道闸门）。

`recordMessage` 只入池，不缩短冷场周期；池非空时跳过搭话，绝不叠加。

## 5. 审批语义（不变）

- **聚合投递**：`from_user` 透传池内最后一位真实 openid（缺省回落到身份映射表），登记审批发起人；
- **冷场搭话 / 定时任务**：系统自发，`from_user` 严格为空，审批保持 Fail-Closed。

`resolveWakeupInitiator` 白名单仍为 `direct / quote / aggregated`。

## 7. 已知风险与待验证项

1. **真机体感**：批次逐条注入后，模型是否按预期一次回复多条、而不是逐条重复应答。
2. **turn/end flush 的时机**：`turn/end` 事件到达时 `agent.status` 仍可能为 `running`，已强制 `followup`
   规避 steer 回旧轮；需真机确认不会与 DSH 的 drain 过程打架。
3. **内存池重启丢失**：进程重启后池清空，重启前的消息不会自动唤醒；与旧布尔标志行为一致，
   DB 仍有记录，可由下一条新消息或 `read_chat_history` 兜底。
4. **投递成功但轮次失败**：`followup` 已被受理即视为投递成功，若该轮模型请求失败，消息不会自动重投；
   符合「宁可晚回，不可重复」的既定取舍。
5. **主动消息日配额**：仍未加压探明，冷场搭话继续严格依赖被动锚点。
