# 交付记录：单聊消息聚合回复与冷场主动搭话

> **状态**：已实现、已装配、已构建；契约测试 32 + 11 + 9 项全绿，全量 714 项测试通过。
> **待办**：**真机验证未做**——模型是否会照指令主动调用 `read_chat_history` 是关键未验证项。

## 1. 最终架构（第三次修订后的定稿）

### 1.1 核心设计：不维护消息池

所有入站消息本就已落库，**数据库是唯一可信源**。管理器只维护一个布尔标志「自上次触发以来是否有新消息」，
绝不复制、裁剪或缓存消息内容。

```ts
interface PeerState {
  hasNewMessage: boolean;          // 是否有待处理的新消息
  lastIdleWakeupAt: number | null; // 上次冷场唤醒时刻；未满一个冷场周期不再唤醒
}
```

早期版本的 `windowStartedAt`、`pending: Message[]`、`fromUsers` 全部删除。

### 1.2 不向模型喂消息

系统事件**只告知「有新消息，去看」**，由模型自行调用 `read_chat_history` 取回内容。
这消除了我们在格式化、附件渲染、上下文裁剪上的全部维护成本，也让模型能按需回溯任意更早的上下文。

聚合提示词骨架：

```
系统事件：[消息聚合] [聚合周期: 2 分钟] [2026-11-13 04:40:34]

会话状态：检测到自上次回复以来有新的用户消息待查看。

（说明：…**你必须先调用 read_chat_history 工具**（建议用 relative 参数按需回溯，如 "30m"、"2h"，
并结合 exclude_self: true 只看对方发言），确认自你上次回复以来对方说了什么，
再判断是否需要通过 send_qq_message 回复。若读取后发现没有需要回应的内容，直接输出 [已回复] 即可。…）
```

### 1.3 自由周期时钟

- 相位来自**插件启动 / 配置启用**时刻，不因消息到达、投递、轮次结束而重置；
- 消息恰好落在 tick 前一秒并被一并带走，属**自然的社交节奏**，不是缺陷；
- 周期配置变更时立即以当前时刻重新对齐相位，避免残留旧节奏；
- 巡检仍以 60 秒扫描驱动，但由内部 `nextTickAt` 判定是否到点，绝不因巡检迟到而补发多次 tick。

### 1.4 两种模式互斥

| | 事件驱动（聚合关闭） | 聚合模式（聚合开启） |
| --- | --- | --- |
| 入站消息 | 立即 `dispatchWakeup`，**进 session** | 仅落库 + 置标志，**不进 session** |
| 模型看到 | 完整消息内容 | 只有一条「去读历史」的 prompt |
| `steer` / `queue` | 生效 | 仅对 tick prompt 生效 |
| 回复时机 | 每条消息一次 | tick 到点且标志为真时一次 |

### 1.5 等待用户输入时跳过唤醒

提问或审批挂起期间**跳过本轮唤醒**，但时钟继续走、标志保留，新消息累积到下一轮由同一 tick 一并处理。
用户明确接受「停顿期间不唤醒、恢复后一次性处理」的语义。

## 3. 入站判定顺序

```
入站 C2C_MESSAGE_CREATE
 ├─ 斜杠命令                    → 立即执行并回执
 ├─ wait_for_user_messages 等待中 → 立即投递收集器
 ├─ 提问回复                    → 立即消费（不进聚合，天然不累积）
 ├─ 审批回复 y/n                → 立即消费（不进聚合，天然不累积）
 ├─ 聚合开启？                  → 落库 + 置标志，不唤醒、不进 session、不发输入中提示
 └─ 其余（聚合关闭）            → 即时唤醒 Agent
```

## 4. 冷场主动搭话

### 4.1 会话口径

用户明确的口径：**不是「不主动骚扰陌生会话」，而是「不为从未出现过的 User 凭空新建 Session」**。

- 候选集 = `peer_openid_map` 中已登记的 peer（`db.getAllPeers()`），等价于「曾经真实互动过」；
- 有记录但无活跃会话 → `sessionManager.ensureSession(peer)` 建会话后唤醒（因为库里有历史可读）；
- 无任何记录 → 根本不进候选集，绝不新建。

### 4.2 发信通道

严格最保守策略：取该 peer 最后一条入站 `msg_id` 做被动回复；内存锚点未命中则回落
`db.getLatestValidInboundSlot`；**两者都拿不到就跳过本轮，绝不降级为纯主动消息**。

### 4.3 沉默起点与重复唤醒

以库中最新入站消息时间为准（`getLatestValidInboundSlot().received_at`），进程重启后依然准确。
出站消息不写入该时间，也不得重置冷场周期。

冷场不是「同一段沉默只唤醒一次」。两道闸门同时满足才再次唤醒：

- 距最近一次入站已满 `idle_reply_timeout_mins`；
- 距上次冷场唤醒也已满同一个周期（本进程内首次没有这道闸门）。

模型调用 `send_qq_message` 或输出 `[结束]` 都不参与判断。用户一直没有入站时，每个冷场周期会再唤醒一次。
`recordMessage` 只置聚合用的「有新消息」标志，不缩短冷场周期。等待用户输入或建会话失败时不记下唤醒时刻，解除后可立即重试。

## 5. 审批语义

- **聚合投递**：源于真实用户入站消息，`from_user` 透传真实 openid，**登记审批发起人**，
  聚合轮次内可正常使用需审批工具与提问工具；
- **冷场搭话 / 定时任务**：系统自发，`from_user` 严格为空，审批保持 Fail-Closed。

`resolveWakeupInitiator` 白名单为 `direct / quote / aggregated`；`agent-runner` 的登记判定已与
`is_system` 解耦——**提示词格式看 `is_system`，审批归属看 `trigger`**。

openid 解析放在 `SystemEventHub`（payload 构造者）而非插件闭包，通过 `resolveOpenid` 回调注入，
便于装配测试直接覆盖。

## 7. 已知风险与待验证项

1. **模型是否照指令调用 `read_chat_history`**——整个方案的关键假设，未真机验证。
   若不调工具，模型将「回复空气」（因为聚合模式下消息不进 session）。
2. **周期节奏的手感**——2 分钟是否合适、tick 撞上运行中轮次时 steer 的体感。
3. **主动消息日配额**——至今未加压探明，故冷场搭话严格依赖被动锚点。
4. **`hasPendingMessage` 的消费时机**——当前 tick 即消费；若模型该轮未回复，消息仍在库中但不会再次唤醒，
   需等下次有新消息才一并读到。用户接受「宁可晚回，不可丢消息」，真机观察是否需调整。
