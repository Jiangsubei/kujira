## 0. 计时语义（第二轮修订）

**不以任何地方为锚点，只以「计时器自己」为准**：

- 用户发消息 → 开始收集并计时；
- 收集期满且**池内有消息** → 组装为一轮唤醒 Agent；
- 收集期满但**池内为空** → 不唤醒（不空转烧 token）；
- 前提：该 peer 存在**当前活跃会话**。

**等待用户输入时暂停**：提问（`ask_user_question`）或审批（y/n）挂起期间，聚合窗口与冷场计时**双双冻结**；用户作答/决策完成后，从此刻**重新累计完整窗口**。

实现方式：暂停期间每轮巡检把两个计时锚点推到当前时刻，等价于「暂停期间不计时」，无需记录暂停起点与恢复时的平移计算。

这一设计绕开了「轮次感知」难题——不需要 `agent.status`、不需要监听 `turn/end`、不需要轮次状态机。因为需要暂停的恰好只有「Agent 卡在等用户输入」这一个状态，用两个 provider 的 pending 表即可精确判定。

> 注：旧 `dsh-napcat-bridge` 并未以轮次结束为计时起点，其三个计时写入点全在消息链路（`recordHumanMessage` / `recordGroupMessage` / `recordDirectWakeup`），`turn/end` 只服务于审批归属。本次的「暂停」语义是新增能力，非移植。

## 1. 与群聊版主动回复的本质差异

旧 `dsh-napcat-bridge` 的 `ProactiveManager` 面向群聊，本次在 Kujira 上重写为单聊版，**未沿用旧实现**，原因有三：

| 维度 | 群聊版（旧） | 单聊版（本次） |
| --- | --- | --- |
| 消息缓冲 | 滑动窗口，`replied` 标记，`proactive_buffer_size` 上限截断 | **无滑动窗口**：池子只装「本轮窗口内未回复消息」，消费即清空，不设条数上限 |
| 巡检周期 | `proactive_interval_mins` 一键双用（既是巡检周期又是冷却窗口） | **巡检固定 60 秒**（`PROACTIVE_CHECK_INTERVAL_MS`），与窗口配置彻底解耦 |
| 开关结构 | 单一总开关捆绑全部子能力，另有随机概率、夜间免打扰等 | **两个完全独立开关**：`aggregation_enabled` / `idle_reply_enabled`，各带独立阈值 |

私聊不需要滑动窗口的根本原因：群聊里不唤醒的消息不进 session，模型天然看不到上下文，才需要缓冲区补上下文；而私聊所有消息本就落在同一 session 内，池子只需要承载「尚未回复」这一批。

## 2. 配置项（15 → 19 项）

| 键 | 类型 | 默认 | 职责 |
| --- | --- | --- | --- |
| `aggregation_enabled` | boolean | `false` | 消息聚合回复总开关 |
| `aggregation_interval_mins` | number | `2` | 周期窗口：每隔多少分钟抓取一次池子 |
| `idle_reply_enabled` | boolean | `false` | 冷场主动搭话总开关 |

## 3. 入站判定顺序（关键设计）

聚合开启后，**普通消息不再即时唤醒**，但以下四类必须前置放行，否则 `/new` 等命令会与普通消息一起被延迟 N 分钟：

```
入站 C2C_MESSAGE_CREATE
 ├─ 斜杠命令                    → 立即执行并回执
 ├─ wait_for_user_messages 等待中 → 立即投递收集器
 ├─ 提问回复                    → 立即消费
 ├─ 审批回复 y/n                → 立即消费
 ├─ 聚合开启？                  → 落入聚合池，不发 msg_type=6 输入中提示
 └─ 其余（聚合关闭）            → 即时唤醒 Agent
```

落库发生在判定之前，因此聚合池消息同样具备短 ID、引用解析与历史可查能力。

## 4. 主动搭话的发信策略

遵循最保守策略，**不赌主动消息配额**：

1. 优先取该 peer 最后一条入站 `msg_id` 做被动回复（内存锚点 → `db.getLatestValidInboundSlot` 兜底）；
2. **两者都拿不到锚点时直接跳过本轮搭话**，绝不降级为无 `msg_id` 的纯主动消息；
3. 底层仍保留 `40034128` / `40034024` 的自动降级能力（既有 `sendSingleWithSlotAndFallback` 逻辑未改动），仅作为兜底而非首选项。

待办：主动消息的真实日/月配额至今未加压探明，若后续探明可再评估是否放开第 2 条门控。

## 5. 审批语义

- **聚合投递**：本质是真实用户消息的延迟投递，`from_user` 透传真实 openid，**登记审批发起人**，聚合轮次内可正常使用需审批工具与提问工具；
- **冷场搭话 / 定时任务**：系统自发，`from_user` 严格为空，审批保持 Fail-Closed。

`resolveWakeupInitiator` 的 `REAL_SENDER_WAKEUP_TRIGGERS` 已扩展为 `direct / quote / aggregated`，且 `agent-runner` 的登记判定已与 `is_system` 解耦——**提示词格式看 `is_system`，审批归属看 `trigger`**。

## 5.1 活跃会话门控

`SessionManager.hasActiveSession(peer)` 为**只读**判定，口径与 `/状态` 命令一致（内存映射 → DB 记录 → 未归档会话兜底扫描）。**刻意不复用 `peerToSessionId()`**，因为后者带有创建与落库副作用，在巡检路径上会凭空造出会话。
