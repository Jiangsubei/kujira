## 1. 与群聊版主动回复的本质差异

旧 `dsh-napcat-bridge` 的 `ProactiveManager` 面向群聊，本次在 Kujira 上重写为单聊版，**未沿用旧实现**，原因有三：

| 维度 | 群聊版（旧） | 单聊版（本次） |
| --- | --- | --- |
| 消息缓冲 | 滑动窗口，`replied` 标记，`proactive_buffer_size` 上限截断 | **无滑动窗口**：池子只装「本轮窗口内未回复消息」，消费即清空，不设条数上限 |
| 巡检周期 | `proactive_interval_mins` 一键双用（既是巡检周期又是冷却窗口） | **巡检固定 60 秒**（`PROACTIVE_CHECK_INTERVAL_MS`），与窗口配置彻底解耦 |
| 开关结构 | 单一总开关捆绑全部子能力，另有随机概率、夜间免打扰等 | **两个完全独立开关**：`aggregation_enabled` / `idle_reply_enabled`，各带独立阈值 |

私聊不需要滑动窗口的根本原因：群聊里不唤醒的消息不进 session，模型天然看不到上下文，才需要缓冲区补上下文；而私聊所有消息本就落在同一 session 内，池子只需要承载「尚未回复」这一批。

## 2. 配置项（15 → 19 项）

| 键 | 类型 | 默认 | 职责 |
| --- | --- | --- | --- |
| `aggregation_enabled` | boolean | `false` | 消息聚合回复总开关 |
| `aggregation_interval_mins` | number | `2` | 周期窗口：每隔多少分钟抓取一次池子 |
| `idle_reply_enabled` | boolean | `false` | 冷场主动搭话总开关 |
| `idle_reply_timeout_mins` | number | `60` | 冷场判定阈值：沉默多久触发搭话 |

均追加在 WebUI「连接与对话」Tab（不新增第 6 个 Tab，避免破坏 `settings-tabs.test.ts` 的 5 分区契约）。窗口与阈值输入框随各自开关联动禁用。

## 3. 入站判定顺序（关键设计）

聚合开启后，**普通消息不再即时唤醒**，但以下四类必须前置放行，否则 `/new` 等命令会与普通消息一起被延迟 N 分钟：

```
入站 C2C_MESSAGE_CREATE
 ├─ 斜杠命令                    → 立即执行并回执
 ├─ wait_for_user_messages 等待中 → 立即投递收集器
 ├─ 提问回复                    → 立即消费
 ├─ 审批回复 y/n                → 立即消费
 ├─ 聚合开启？                  → 落入聚合池，不发 msg_type=6 输入中提示
 └─ 其余（聚合关闭）            → 即时唤醒 Agent
```

落库发生在判定之前，因此聚合池消息同样具备短 ID、引用解析与历史可查能力。

## 4. 主动搭话的发信策略

遵循最保守策略，**不赌主动消息配额**：

1. 优先取该 peer 最后一条入站 `msg_id` 做被动回复（内存锚点 → `db.getLatestValidInboundSlot` 兜底）；
2. **两者都拿不到锚点时直接跳过本轮搭话**，绝不降级为无 `msg_id` 的纯主动消息；
3. 底层仍保留 `40034128` / `40034024` 的自动降级能力（既有 `sendSingleWithSlotAndFallback` 逻辑未改动），仅作为兜底而非首选项。

## 5. 审批语义

- **聚合投递**：本质是真实用户消息的延迟投递，语义上仍是真人触发；
- **冷场搭话**：系统自发，无任何真实用户输入。

本次两类事件在 `SystemEventHub` 中均标记 `is_system: true`、`from_user: ''`，因此**审批统一保持 Fail-Closed**。这是偏保守的选择——聚合轮次中模型无法执行需审批工具。若后续希望聚合轮次保留审批能力，需将 `aggregated_messages` 的 `from_user` 透传为真实发送者身份，并同步调整 `TurnInitiatorTracker` 的登记口径。
