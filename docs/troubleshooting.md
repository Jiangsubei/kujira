# 常见问题排查与技术实测手册 (Troubleshooting)

本文档汇总了在部署与运行 **kujira** 过程中可能遇到的连接异常、配置报错，并系统公开了沉淀于 `devlog/archive/` 中的 **QQ 官方 Bot API v2 真实真机实测边界与踩坑结论**。

---

## 1. 连接与网关异常排查

### 1.1 机器人无法连接网关 / 启动报鉴权失败 (401 Unauthorized)
- **原因分析**：
  1. `AppID` 或 `密钥 (AppSecret)` 填错，或者在复制时夹带了前后不可见空格；
  2. 在 QQ 开放平台重置了密钥，但未在 DSH 设置面板中同步更新；
  3. 网络环境无法访问腾讯 OpenAPI 域名（`https://api.sgroup.qq.com`）。
- **解决方案**：
  - 访问 QQ 开放平台后台，重新生成 `AppSecret`；
  - 打开 DSH WebUI 或桌面端设置面板，在「连接设置」重新输入 `AppID` 与新生成的 `AppSecret` 并保存；
  - 在服务器/本地终端执行 `curl -I https://api.sgroup.qq.com` 确认网络连通性。

### 1.2 WebSocket 网关频繁断连与心跳超时
- **原因分析**：
  - 本地网络存在代理软件或防火墙拦截长连接（WebSocket Ping/Pong）；
  - DSH 所在宿主机休眠导致心跳中断。
- **解决方案**：
  - Kujira 网关客户端内置指数退避重连机制，网络恢复后会自动发送 `Resume` 恢复会话；
  - 若处于代理环境中，请在代理客户端中将 `*.qq.com` 与 `*.sgroup.qq.com` 加入直连白名单。

## 2. QQ 官方 Bot API 协议硬性限制与实测避坑

> [!WARNING]
> **一切以实测为准，切勿轻信腾讯官方文档陈旧表述**：
> 官方开放平台公开文档存在多处与线上生产行为不符或滞后的说明。以下技术边界均来自项目真实探针与真机测试（见 `devlog/archive/QQ官方Bot_API实测与踩坑/`）。

### 2.1 被动回复机制实测真相与四大真实陷阱 (`50015001` / `40054005` / `40034024` / `40034128`)

许多开发者直接照搬腾讯官方文档，导致在被动消息、流式与槽位设计上踩进深坑。项目在 `devlog/archive/QQ官方Bot_API实测与踩坑/实测报告-被动回复窗口主动消息与msg_seq去重机制.md` 中进行了高强度真实真机探针测试，以下为确凿事实：

#### 陷阱一：打破官方文档「60 分钟 / 4 次限制」神话
- **官方文档声称**：单聊被动消息「有效时间 60 分钟，每条消息最多回复 4 次」（超限返回 `40034128 被动回复时间或次数超限`）；
- **线上真机实测**：
  - 同一真实入站 `msg_id`，`msg_seq = 1..6` 连发 6 条普通文本：**全部 200 成功送达**，未见 `40034128`；
  - 同一入站 `msg_id` 累计发送 20 条富媒体（`msg_type=7`）：**全部送达成功**；
  - 取 **4.4 小时前（266 分钟）甚至 28 小时前跨天**的真实入站 `msg_id` 发起被动流式与文本：**全部 200 成功**；
- **工程结论**：官方文档所写的「60 分钟 / 4 次」在线上环境**当前均未被强制执行**。工程上严禁在应用层生硬写死 60 分钟失效或 4 次计数器拦截，但需防范平台后续收紧策略。

---

#### 陷阱二：流式接口禁止无 `msg_id` 主动发送 (`50015001`)
- **实测现象**：
  - 普通单聊发送接口（`POST /v2/users/{openid}/messages`）不传 `msg_id` / `msg_seq`（作为纯主动消息）：实测 **200 成功下发**，未报权限错误；
  - 但**流式接口（`POST /v2/users/{openid}/stream_messages`）若不传 `msg_id`，连续多次必报**：
    ```json
    { "code": 50015001, "message": "系统繁忙，请稍后重试" }
    ```
- **真实根因**：官方报错提示为模糊的“系统繁忙”，实测本质是**流式通道完全不支持无 `msg_id` 的纯主动模式**！同一端点只要补上历史入站 `msg_id` 即可瞬间 200 成功；
- **Kujira 应对**：流式出站通道严格要求绑定有效入站锚点。

---

#### 陷阱三：`(msg_id, msg_seq)` 去重机制与跨天残留 (`40054005`)
- **平台去重原理**：官方服务端针对每一条入站消息，依据 `(msg_id, msg_seq)` 二元组执行幂等去重；
- **真实陷阱**：
  1. **跨通道共享**：流式消息（`append` / `replace`）、普通文本与富媒体**共享同一 `msg_seq` 空间**。若前序流式用过了 `msg_seq=1, 2`，后续普通消息再传 `msg_seq=1` 必被拒绝；
  2. **跨天残留**：去重记账**会跨天持久留存**！前一天在某个 `msg_id` 上消耗了 `msg_seq = 1..5`，次日复用该 `msg_id` 时若又从 `msg_seq=1` 起步，接口直接报：
     ```json
     { "code": 40054005, "message": "消息被去重，请检查请求msgseq" }
     ```
- **Kujira 应对**：
  - 维护持久化 `inbound_reply_slots` 与内存 `MsgSeqSlotAllocator`，记录 `last_seq`，确保每条出站消息的 `msg_seq` 严格单调递增；
  - 遭遇 `40054005` 时自适应递增槽位并自动无损重试。

---

#### 陷阱四：入站 `msg_id` 与出站响应 `body.id` 混淆 (`40034024`)
- **实测现象**：
  - 入站消息（`C2C_MESSAGE_CREATE` 的 `d.id`）与机器人出站发送成功返回的 `body.id` 均采用相同的 `ROBOT1.0_...` 前缀；
  - 若错误地将上一条机器人发出的出站 `body.id` 当作后续发消息的被动 `msg_id` 传入，接口直接拒绝：
    ```json
    { "code": 40034024, "message": "请求参数msg_id无效或越权" }
    ```
  - **严重误导**：此报错极易被开发者误判为“被动回复窗口过期”，实际上是传错了 ID 来源；
- **Kujira 应对**：
  - 执行严格的入站/出站 ID 物理隔离，`inbound_reply_slots` 仅且必须写入来自用户入站事件的 `d.id`；出站 `id` 仅登记在 `messages` 表用于消息撤回。

---

#### 陷阱五：真实失效锚点的优雅降级 (`40034128` / `40034024`)
- 当历史入站锚点确实因平台清理失效而触发 `40034128` 或 `40034024` 时，Kujira 会在 `InboundReplySlots` 中将该锚点标记为 `invalidated = 1`，并自动平滑降级为**无 `msg_id` 的普通主动消息**下发，确保消息绝对不丢失。

---

### 2.2 消息撤回 2 分钟硬时限 (`40064004` / `40061002`)

- **实测现象**：
  - 大模型调用 `recall_message` 撤回较早的消息时失败，接口返回 `40064004` 或 `40061002`。
- **官方真机边界**：
  - 腾讯平台对单聊（C2C）消息撤回有 **120 秒（2 分钟）硬性时间窗口**，超过 120 秒物理禁止撤回；
  - 机器人仅能撤回自身发出的消息，绝不允许撤回对方（用户）的消息。
- **排查建议**：
  - 属于官方底层限制，Agent 工具已对此类错误做了捕获并返回友好提示，无需干预。

---

### 2.3 单聊 Markdown 渲染规范与限制

- **实测现象**：
  - 发送的 Markdown 在手机 QQ 上未能成功渲染为富文本，直接展示为原始符号。
- **官方真机边界与排查细节**：
  1. **标题空格规范**：腾讯 Markdown 解析器严格遵循 CommonMark 规范，`#` 后**必须保留一个半角空格**（如 `# 标题` 会被正常渲染，而 `#标题` 会被降级为纯文本）；
  2. **外链域名白名单**：Markdown 中的超链接 `[文字](url)` 仅允许腾讯开放平台已备案过审的域名，普通未备案外链会被自动过滤或直接无法点击；
  3. **表情符号限制**：单聊中 `<emoji:id>` 标签不会被渲染，建议直接使用标准 Unicode Emoji（如 `😄`, `🚀`）。

---

### 2.4 富媒体四步分片上传实测细节 (`send_file`)

- **官方文档勘误**：
  - 官方文档声称分片编号从 `0` 开始（0-based），**实测线上完全相反，分片 index 必须为 1-based（从 1 开始）**，传 0 会直接返回参数非法；
  - 单片大小（`block_size`）推荐固定为 `524288` 字节（512KB）；
  - 上传完成后取得的 `file_info` 在短时间内支持秒级复用，同一图片/文件无需重复上传。

## 3. 仿生时钟与消息聚合问题排查

### 3.1 为什么发送消息后，机器人没有立刻回复？
- **原因**：
  - 当前开启了 `aggregation_enabled: true`（连续消息聚合）；
  - 系统在收到第一条消息后，会在 `[aggregation_min_seconds, aggregation_max_seconds]`（默认 10s~60s）之间随机采样等待时长，给用户留出补充打字的空间。
- **调优方案**：
  - 若追求极速响应（例如工作助手场景），可在设置面板中：
    1. 将 `aggregation_min_seconds` 设为 `3`；
    2. 将 `aggregation_max_seconds` 设为 `10`；
    3. 开启 `instant_reply_enabled: true`（高活跃度下概率秒回）。

### 3.2 为什么我还在连续打字，机器人突然“抢话”打断了？
- **原因**：
  - 此为 Kujira 的核心设计：**触底下限锁定防饥饿机制**；
  - 当您连续追加多条消息时，剩余时间会按 25% 温和折减。一旦折减到达硬底线时刻（`FloorTime = 首条时间 + aggregation_min_seconds`），系统判定用户已有足够多的输入，立即锁定并打断投递，防止无休止打字导致对话迟迟无法开始。

## 4. 记忆、黑话与存储问题排查

### 4.1 记忆更新失败并报错“超出字符预算”
- **原因**：
  - 用户画像或会话规则单文件字符数超过了 `user_profile_budget_chars`（默认 2200 字符）或 `session_memory_budget_chars`（默认 2200 字符）。
- **设计哲学**：
  - 这是 Kujira 的刻意设计，用于硬性阻止大模型将每次琐碎的闲聊无限制追加到记忆库中，避免上下文被撑爆；
  - 收到报错后，大模型会自动对已有记忆进行摘要整理，删除临时排查过程，只保留长期稳定事实后再次尝试写入。

### 4.2 SQLite 数据库锁定 (Database is locked)
- **原因**：
  - 多进程或外部 SQLite 客户端同时打开了 `.dsh/kujira/` 下的 `.db` 文件。
- **解决方案**：
  - 关闭外部数据库查看软件（如 DB Browser for SQLite），重启 DSH 服务。

## 5. 项目内置探针脚本 (Probes)

为了保持“一切以实测为准”的技术底色，项目在 `scripts/` 下内置了一组专业探针工具。当您对官方线上 API 行为产生疑问时，可随时运行验证：

```bash
# 1. 网关连通性与凭据探测
pnpm probe:qq

# 2. 被动回复窗口与主动消息 (50015001) 探针
pnpm probe:active

# 3. 单聊文本长度上限与流式下发探针
pnpm probe:e3

# 4. 入站引用卡片与多媒体解构探针
pnpm probe:quote
```
探针执行日志将即时输出真实 HTTP 状态码与官方返回体，为您的二次开发与深度调优提供第一手铁证。
